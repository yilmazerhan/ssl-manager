Planning Document

SSL Sentry — a certificate lifecycle management platform

A system of record for every TLS certificate the organization issues: what exists, when it expires, and how it gets renewed — with Let's Encrypt and ZeroSSL wired in as certificate authorities, a scheduler that renews before anything lapses, an API for machines, and a web UI for the people who own the domains.

01 Overview & scope

Six capabilities were asked for. Each maps to one module below, and the modules share one database and one auth layer rather than being six separate tools glued together.

Certificate store

Encrypted storage for issued certs, chains, and private keys, with full version history.

Inventory

Searchable list of every cert with expiry, issuer, SANs, and owning team surfaced up front.

CA integrations

Let's Encrypt via ACME v2, ZeroSSL via its REST API — one abstraction, two providers.

Renewal

Automatic renewal ahead of expiry, plus a manual "renew now" for any certificate.

API

Machine-to-machine access to inventory and certificate material, scoped and audited.

Web UI

Authenticated download of certs and keys, gated by role, with every fetch logged.

02 System architecture

Four tiers: a web UI and API sit on shared application logic; that logic talks to a metadata database and a secrets backend; a scheduled worker drives issuance and renewal against the two certificate authorities.

Why one worker, not two

Let's Encrypt and ZeroSSL both reduce to the same three steps — prove domain control, submit a CSR, retrieve the chain — so the renewal worker talks to a single internal CertificateAuthority interface with two implementations, rather than special-casing a provider throughout the codebase.

04 CA integrations

Both providers are ACME-capable, but the plan uses each one's strongest path rather than forcing both through identical plumbing.

Let's Encrypt — ACME v2

  • Integrate via a maintained ACME client library (e.g. lego for Go, acme.sh/certbot if shelling out is acceptable) rather than implementing ACME from scratch.
  • HTTP-01 challenge for single, internet-reachable domains — simplest path, no DNS API access needed.
  • DNS-01 challenge for wildcards and internal/non-public domains — requires a DNS provider plugin (Route 53, Cloudflare, etc.) with scoped write access to create the _acme-challenge TXT record.
  • Certificates are valid 90 days; the renewal engine targets 30 days before expiry by default.
  • Rate limits apply per registered domain per week — the app tracks issuance attempts to avoid hitting them during retries.

ZeroSSL

  • Two integration paths exist; the plan uses the native REST API (api.zerossl.com) as the default, since it needs no ACME client and supports CSR upload directly.
  • ACME + External Account Binding (EAB) is kept as a fallback path for environments that already run an ACME client and just want to point it at a second CA.
  • Domain validation via CNAME or HTTP file token — email validation is avoided for automation since it requires a human to click a link.
  • ZeroSSL supports 90-day free certs and paid multi-year certs; both are modeled the same way in certificate.

05 Certificate creation flow

Creating a certificate from scratch is not one atomic action — domain validation takes time, and sometimes needs a human to change a DNS record by hand. The wizard models this as an order that moves through states, so the user always knows what's next instead of watching a spinner.

1 — Domains user input

Enter the common name and any additional SANs, including wildcards (e.g. *.kron.com.tr). The wizard flags domains already covered by an active certificate before letting the user continue.

2 — Certificate authority user choice

Choose Let's Encrypt or ZeroSSL. The wizard shows each option's validity period, wildcard support, and cost side by side before the user commits.

3 — Validation method user choice

HTTP-01 (host a token file), DNS-01 (create a TXT record), or ZeroSSL's CNAME/file check. If a DNS provider is already connected with scoped credentials, DNS-01 completes automatically instead of by hand.

4 — Key & CSR generation system

The app generates a key pair (algorithm chosen by the user — RSA-2048/4096 or ECDSA P-256) directly inside Vault and builds the CSR from it. The private key is never returned to the browser at this or any later step.

5 — Prove domain control system + user

Automated challenges complete unattended. Manual challenges show exact instructions — the record name and value, or the file path and contents — plus a "Check now" button that polls until the CA can see it.

6 — Issuance system

Once validation passes, the CSR is submitted to the chosen CA. The order polls the CA until the signed certificate and chain come back.

7 — Ready system

The order resolves into a new certificate and its first version, added to inventory under the requesting user's team, with auto-renew on by default. It's downloadable immediately and tracked by the renewal engine from this point forward.

Order states

StateMeaning
draftDomains and CA chosen, not yet submitted
awaiting_validationChallenge issued; waiting on DNS/HTTP proof, automatic or manual
issuingValidation passed; CSR submitted, waiting on the CA
issuedCertificate stored, order closed, inventory row created
failedValidation or issuance error, reason shown; order can be retried from step 3

06 Renewal engine

One scheduled job, run daily, drives both automatic and manual renewals through the same code path — a manual "renew now" click in the UI just runs the same job early, for one certificate.

  1. Scan certificate for rows where auto_renew = true and days-to-expiry ≤ renew_before_days (default 30).
  2. Generate a new key pair (or reuse the existing one, per policy) and a CSR for the certificate's domain set.
  3. Submit to the recorded ca_provider through the CertificateAuthority interface; complete the domain validation challenge.
  4. On success, write a new certificate_version row, update certificate.not_after, and push the new material to any downstream target (load balancer, CDN, secret store consumers).
  5. On failure, retry with exponential backoff (up to 3 attempts across 24 hours); if still failing, escalate to a critical alert rather than retrying silently forever.
  6. Record the outcome to audit_log either way.

Failure modes worth designing for up front

FailureHandling
DNS/HTTP challenge unreachableRetry with backoff; alert owning team, not just platform team
CA rate limit hitQueue and retry after the limit window; never hammer the CA
Worker itself is downRun as two replicas with a leader lock — a missed renewal is an outage
Downstream push fails after issuanceNew version is already stored — retry the push independently, don't re-issue

07 API design

A versioned REST API, authenticated with API keys or OAuth2 client-credentials for machine callers. Certificate metadata and certificate material are separate endpoints with separate scopes — reading the inventory should not imply the right to export a private key.

MethodPathPurposeScope
GET/api/v1/certificatesList/search/filter inventorycerts:read
GET/api/v1/certificates/{id}Full metadata for one certificatecerts:read
GET/api/v1/certificates/{id}/downloadFetch PEM / chain / key bundlecerts:export
GET/api/v1/certificates/{id}/historyPrior versions and renewal eventscerts:read
POST/api/v1/certificate-ordersStart a from-scratch order: domains, CA, validation methodcerts:issue
GET/api/v1/certificate-orders/{id}Poll order status and challenge instructionscerts:read
POST/api/v1/certificate-orders/{id}/validateTrigger a validation check for a manual challengecerts:issue
POST/api/v1/certificates/{id}/renewTrigger renewal on demandcerts:issue
DELETE/api/v1/certificates/{id}Revoke and retire a certificatecerts:admin

Issuing a certificate from scratch is asynchronous, so it's modeled as a resource of its own — certificate_order — rather than a single call that blocks until a CA responds. An order resolves into a normal certificate once status reaches issued, at which point the usual read/download/renew endpoints apply to it. Every request is logged with caller identity, scope used, and resource touched. Downloads of key material additionally require a short-lived, single-use download token issued after an explicit UI confirmation — an API key alone cannot silently exfiltrate a private key.

Login is via the organization's existing OIDC provider (Azure AD / Okta / Google) — no separate password store. Downloading private key material requires MFA to have been asserted in the current session, not just a valid cookie.

09 Key & secret handling

  • Private keys are generated and stored in Vault (or a cloud KMS); Postgres holds only a reference, never the key bytes.
  • Certificate PEMs and chains are encrypted at rest with envelope encryption; TLS in transit everywhere, including between internal services.
  • ACME account keys and ZeroSSL API credentials are themselves Vault secrets, scoped per environment, rotated on a schedule.
  • Every read, download, issuance, and renewal writes an append-only audit row — who, what, when, from where.
  • Access follows least privilege by default: a Cert Manager sees only their team's certificates unless explicitly granted broader scope.

11 Technology stack

Backend

Go — pairs naturally with mature ACME tooling (lego) and gives the renewal worker predictable concurrency.

Frontend

React + TypeScript, a component library over hand-rolled CSS for the inventory table and forms.

Database

PostgreSQL for metadata, roles, and the audit log.

Secrets

HashiCorp Vault (or cloud KMS/Secrets Manager) for private keys and CA credentials.

Scheduling

A Kubernetes CronJob or a workflow engine (Temporal) for the renewal scan and retry logic.

Observability

Structured logs, metrics on renewal success rate, and the audit log itself as a compliance artifact.

12 Delivery roadmap

Ordered so each phase is independently useful — the platform is worth having after Phase 1, not just after Phase 5.

Phase 1 — Inventory & visibility MVP

Manual certificate upload, expiration dashboard, read-only API, OIDC login and RBAC scaffolding. Solves "we don't know what's about to expire" on day one.

Phase 2 — Let's Encrypt automation

ACME v2 client, HTTP-01 issuance, automatic renewal at the 30-day threshold, and the notification pipeline.

Phase 3 — ZeroSSL & wildcards

ZeroSSL REST integration, DNS-01 challenge support for Let's Encrypt, wildcard certificate issuance for both providers.

Phase 4 — Hardening

Vault-backed key storage, full audit logging, download tokens with MFA re-assertion, webhook integrations for downstream consumers.

Phase 5 — Scale & resilience

Leader-locked worker replicas, multi-team/multi-tenant scoping, CT-log cross-checking, disaster recovery drills for the cert store.
